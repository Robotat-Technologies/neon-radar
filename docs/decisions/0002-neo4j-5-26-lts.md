# 0002. Neo4j 5.26 LTS

- **Status:** proposed
- **Date:** 2026-10-21
- **Deciders:** @robotat-com (tech lead)

## Context

NeonRadar stores its graph in Neo4j Community Edition, run locally in Docker Compose (`docs/build/PHASE-1.md` sections 0.4 and 4.1). Every developer, CI job and AI session should run the same server, with APOC and Graph Data Science (GDS), bound to localhost and with no outbound calls at runtime (guardrail G3). The project runs until 20 November 2026 and must not move under the squads in that time.

The facts that shape the decision (checked on 16 October 2026 unless a later date is given):

- **Release lines.** Neo4j moved to calendar versions in 2025; the newest calendar release was 2026.09.0, and each calendar release is supported only until the next one. 5.26 is the long-term-support line, supported until June 2028 with fixes but no new features; its newest patch is 5.26.32 (`docs/research/2026-10-16/neo4j.md` section 1, `stack.md` 1.1).
- **Cypher.** 5.26 runs Cypher 5 only. Calendar images from 2026.02 create databases with Cypher 25 by default. New Cypher features land only in Cypher 25, but quantified path patterns, `SHORTEST`, `CALL { } IN TRANSACTIONS` and full-text indexes all exist in 5.26 (`neo4j.md` section 4).
- **Plugins in the image.** `neo4j:5.26.32-community` ships APOC Core 5.26.32 in `labs/`. It does not ship GDS: on 2026-10-21 the image layers held only `neo4j-genai-plugin-5.26.32.jar` and `neo4j-fleet-management-plugin-1.2.0-v5.jar` in `products/`. This agrees with `stack.md` 1.4 and contradicts `neo4j.md` section 2 and `PHASE-1.md` 3.1 ("bundles ... GDS 2.13.14").
- **GDS download at start.** With `NEO4J_PLUGINS='["graph-data-science"]'`, the image's entrypoint (`/startup/docker-entrypoint.sh`, read on 2026-10-21) fetches `https://graphdatascience.ninja/versions.json` and downloads the jar on every container start, without checking for an earlier copy. Offline, it starts without GDS. That breaks G3 and the offline promise.
- **GDS jars on allowed hosts** (checked 2026-10-21): the GitHub releases of `neo4j/graph-data-science` carry jars for the 5.26 line only up to 2.13.4 (15 April 2025), although tags go up to 2.13.14. GitHub publishes no checksum for that asset. The jar inside the release zip has the same SHA-256 as the standalone jar. neo4j.com's Deployment Center offers only the newest GDS, served from graphdatascience.ninja.
- **GDS Community limits.** All algorithms, at most 4 CPU cores and at most 3 models in the catalog (`neo4j.md` section 2).

## Options considered

1. **Neo4j line.**
   - **2026.09 calendar release:** Cypher 25 and newer features, but a new release every month, each supported only until the next, and a 2026 LTS announced but not yet released.
   - **5.26.32 LTS:** support until June 2028, no feature churn during the project, and the Cypher dialect AI models know best. The cost is no Cypher 25, and a migration once the 2026 LTS is adopted.
2. **How GDS gets into the container.**
   - **`NEO4J_PLUGINS` with `graph-data-science`:** no extra step, but a download from graphdatascience.ninja on every start, and no GDS when offline.
   - **A pinned jar fetched once:** an explicit `make plugins` step pulls the image and downloads a checksum-pinned jar into `data/cache/neo4j-plugins/`. `make up` only checks that both are present and starts offline. The operator chose this option on 2026-10-21 (G3; OD-13).

## Decision

We will:

- Run **`neo4j:5.26.32-community`**, pinned exactly in `compose.yaml` (later also in the devcontainer, Testcontainers and CI), and write the forward-compatible Cypher 5 subset (`PHASE-1.md` 5.2), so that queries keep running under Cypher 25.
- Install **APOC Core from the image** (`NEO4J_PLUGINS='["apoc"]'`).
- Install **GDS 2.13.4** from the GitHub release asset, pinned by SHA-256 `10e072f73992224f1159f246c9d6a89da5f3b3434aeffa5be42647edda13a8d8` in `scripts/fetch_gds.sh`. GitHub publishes no checksum for this asset, so the SHA-256 was taken from the first download (2026-10-21) and cross-checked against the jar inside the release's zip asset, which has the same hash.
  - `make plugins` is the only step that uses the network: it pulls the image and downloads the jar once. `make up` never pulls (`docker compose up --pull never`) and refuses to start without the image or the verified jar.
  - Compose mounts `data/cache/neo4j-plugins/` read-only at `/nr-plugins`, and a one-line entrypoint wrapper copies the jar into `/var/lib/neo4j/plugins/` before the image's entrypoint runs. The folder is mounted outside `/var/lib/neo4j` and `/plugins` because the image's entrypoint chowns both on every start: a read-only mount there stops the container, and a writable one would hand the host folder to uid 7474 on Linux.
  - `NEO4J_dbms_security_procedures_unrestricted` is set to `apoc.*,gds.*` explicitly.
- **Switch off product analytics and usage reports** with these settings, verified against the Neo4j 5 Operations Manual configuration reference, https://neo4j.com/docs/operations-manual/5/configuration/configuration-settings/ (read 2026-10-21). Neo4j validates configuration strictly (`server.config.strict_validation.enabled=true`), so a container that starts is the test:

  | Setting | Environment variable | Default | Result on 5.26.32 Community |
  |---|---|---|---|
  | `client.allow_telemetry` ("Configure client applications such as Browser and Bloom to send Product Analytics data") | `NEO4J_client_allow__telemetry=false` | true | set; `SHOW SETTINGS` reports `false` |
  | `dbms.usage_report.enabled` ("Usage data reporting", since 5.20) | `NEO4J_dbms_usage__report_enabled=false` | true | set; `SHOW SETTINGS` reports `false` |
  | `browser.allow_outgoing_connections` (labelled Enterprise Edition in the manual) | `NEO4J_browser_allow__outgoing__connections` | true | not set: Community refuses to start with "Unrecognized setting. No declared setting with name: browser.allow_outgoing_connections" |
  | `server.bolt.telemetry.enabled` (driver telemetry collected by the server; the manual labels it "Introduced in 5.4", which most likely means Bolt protocol 5.4, the version that added the `TELEMETRY` message, https://neo4j.com/docs/bolt/current/bolt/message/; the Neo4j release that added the setting is not verified) | none | false | left at its default (`false`) |

  On the client side, `neonradar_graph.client.get_driver()` creates the driver with `telemetry_disabled=True`, so the driver never sends telemetry either.

- **Bind ports 7474 and 7687 to `127.0.0.1` only**, and size memory by two profiles: standard (heap 2G, page cache 2G, container limit 5g) and small (1G, 512M, 2500m). See `docs/architecture/local-stack.md`.
- **Revisit** when the 2026 LTS is released and GDS, APOC, the Python driver and neo4j-graphrag support it.

## Consequences

- **Stable for the project window.** Nothing moves until a reviewed pull request bumps the pin. Cypher 25 features (`SEARCH`, `FOR`, `LET`, path modes) are not available. Online upgrades from 5.26 LTS to 2025 and 2026 releases are supported (`neo4j.md` section 1).
- **Offline starts.** Once the image and the jar are present (one `make plugins`), `make up` makes no outbound calls, the server sends no analytics or usage reports, and the driver sends no telemetry. Neo4j Browser's own outgoing connections cannot be switched off on Community; the browser runs on the developer's machine.
- **GDS is an older 2.13 patch.** GDS 2.13.4 runs on Neo4j 5.26.32: `gds.version()`, `gds.list()` (446 procedures) and `gds.wcc.stats` on a generated graph all ran on 2026-10-21. It lacks the fixes in 2.13.5 to 2.13.14. Move to a newer 2.13 patch once one is published on an allowed host.
- **Licence question for humans.** The two licence files inside the GDS 2.13.4 jar contradict each other (read on 2026-10-21):
  - `LICENSE.txt` is the "Neo4j, Inc. Pre-release Agreement for Neo4j Software". It grants a licence to use the software "solely internally and solely for evaluation purposes" for a "Pre-release Period" that ends at the earlier of "the thirty (30) day anniversary date of the Effective Date" and general availability. It "expressly" prohibits "distributing any copy of the Software ... to any third party". It says use is also subject to the Neo4j User Experience Improvement Program (https://neo4j.com/legal/neo4j-ux-improvement-program/), and that the software "should not be used in a production or commercial operating environment".
  - `NOTICE.txt` says the software developed by Neo4j "is licensed under the GNU GENERAL PUBLIC LICENSE Version 3 ... to all third parties" unless a commercial agreement applies, and that the licence "is included in the LICENSE.txt file". That file holds the pre-release agreement instead.
  - NeonRadar does not redistribute the jar: each user downloads it with `make plugins`. The same question applies to the jar the image's entrypoint would download from graphdatascience.ninja. Which licence governs the GDS Community jar, and whether NeonRadar may tell users to download it, is for the data steward and the project lead to decide (OD-5). `neo4j.md` section 2 already flagged it as unverified.
- **Follow-up work.**
  - Testcontainers and CI (M1.6, M1.7b) should use the same pinned jar instead of `NEO4J_PLUGINS` with `graph-data-science`, which downloads it on every start (OD-13).
  - M1.5 (devcontainer): `initializeCommand` must be `bash scripts/ensure_env.sh && bash scripts/fetch_gds.sh`, because `compose.yaml` mounts `data/cache/neo4j-plugins` with `create_host_path: false` and the container cannot start without it.
  - M1.9e: `make demo-mini` must start Neo4j through `make up` (or run `bash scripts/fetch_gds.sh --check` first), and `e2e.yml` must run `make plugins`, with a cache keyed on the jar's SHA-256.
  - The entrypoint wrapper depends on the image's `tini` and `/startup/docker-entrypoint.sh`: check both when the image pin changes.
