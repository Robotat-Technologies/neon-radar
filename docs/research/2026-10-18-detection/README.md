# NeonRadar research notes, 18 October 2026 (detection)

These four notes are the evidence behind `docs/build/PHASE-3.md` and its code book. Research agents wrote them on 18 October 2026 by checking primary sources (the Cypher, GDS, APOC and driver sources at fixed commits, PyPI and Docker Hub, regulators' and standard setters' publications, the legislation itself, the papers behind the public AML datasets) and, where they could, by running code. ## Where the build spec decided differently

The spec wins where it differs from a note; the notes keep what was found on the day.

1. **Path typologies.** `detection-cypher-gds.md` 0 recommends quantified path patterns anchored on the first hop, pruned per iteration against it and post-filtered for time order. The spec expands one hop per query from Python instead (`expand.py`, 7.1.3), because the layering chain needs each hop compared with the previous one, which a Cypher 5 pattern cannot do, and because the same detector code must also run on the in-memory oracle.
2. **Query files.** The note's section 2 sketches 43 query files for fourteen typologies. The spec's detectors share the 29 methods of one `Source` interface in 33 files (one per method, four for the GDS ring step, plus the evidence query), written for the oracle-and-Neo4j design.
3. **Transaction memory.** The note suggests `db.memory.transaction.max` of about 1 GB. The spec keeps Phase 2's memory profile and has M3.9 record any query that hits a limit before anything is tuned.
4. **Louvain.** The plan mentioned community detection. The spec uses weakly connected components only, for the ring variant of `fan_in_collection`, because Louvain is not repeatable at a concurrency above 1 (`detection-cypher-gds.md` 4) and the published figures must be repeatable.
5. **Structuring thresholds.** `typology-detection-definitions.md` 1 proposes rule sets per currency (`us_ctr`, `uk_hvd`, `eu_amlr_cdd`), a secondary 3,000 threshold for USD and a 30-day window for money remitters. The spec keeps one threshold with `below_inclusive_currencies` (which gives the same result for the three 10,000 thresholds), no secondary threshold, and one window, because C2 has no account type for money remitters.
6. **Layering splits and merges.** The note allows them (`allow_split_merge`). The detector does not follow them; the `split_chain` scenarios measure what that costs (7.3.3, 7.6.5).
7. **Fan-in across banks.** The note's multi-bank indicator (three banks within 20 days) is not built: C2's accounts carry a bank name but no institution identity a detector could rely on.
8. **Dormancy burst.** The note's "10 times the pre-gap monthly mean, or at least 50,000" becomes the larger of the two, so a quiet account with a tiny history still needs 50,000 to qualify.
9. **Sanctions transfers near a designation date.** The note's red flag (ownership changes within 90 days of a designation) is not built in Phase 3.
10. **The CI gate.** `evaluation-alerting.md` 3 proposes a committed one-seed fixture, a recall floor and nightly development runs. The spec commits no world (2.9): CI regenerates seed 1, which the generator makes byte for byte the same, and compares exact counts per typology with `eval/baselines/ci.json`, which names every change; development runs are on demand.
11. **Alert kinds.** The note counts four kinds (true, duplicate, look-alike, background). The spec adds `partial` and `other` (an alert on another typology's scenario), so that precision's denominator is explained in full (7.6.2).
12. **Explanations and grouping.** The note proposes optional C4 1.1.0 fields (`explanation.conditions`, `strength_terms`) and grouping overlapping alerts with a `group_id`. The spec keeps C4 at 1.0.0 (decision 10) and removes only identical alerts; grouping and counterfactual explanations are left to Phases 4 and 5.
13. **Background period and detail.** `synthetic-transactions.md` 2 recommends 24 months of background, payment schemes (Faster Payments, Bacs, CHAPS) with their timing, larger counterparty sets and background dormancy. The spec generates 18 months (2025-01-01 to 2026-07-01, within the committed bank holiday table), uses the C1 channels only (C1 cannot carry a scheme, 5.1), smaller counterparty pools, and no background dormancy (dormant accounts come only from scenarios and look-alikes), to keep worlds small and the base organisations' profiles plain.
14. **Real overlays.** The note's overlay for real entities is loaded additively with `--no-replace`. The spec defines its own load rule, C2 L18, which removes the previous overlay and all detection results first, and loads into `neo4j-real` only for the profiles the data steward lists (5.2, 7.7).
15. **Alerts about real entities.** The notes describe structural-pattern wording for alerts that touch real entities. The spec goes further (decision 2, G12): payment-based findings that involve a real entity, and findings that name a real person anywhere, as subject or in the evidence, are withheld and only counted. Every legal entity that is not an organisation counts as a person, so an ICIJ officer or intermediary whose kind the source does not state is treated as one.
16. **The sanctions reporting floor.** `typology-detection-definitions.md` 10.6 gives no floor below which an exposure is not reported. The spec reports an organisation whose summed recorded holdings of listed parties can reach 25 percent (`min_reported_share`, a modelling choice: the PSC register's floor), and words every regime's result in full sentences in the summary rather than in the headline (7.3.10).
17. **ICIJ's caution.** `typology-detection-definitions.md` 16.1 quotes ICIJ's disclaimers. The spec puts ICIJ's caution among the notes of every alert whose evidence holds an ICIJ record (7.5.1), as Phase 1's dataset register asks.

## Before you rely on a fact

These notes are a snapshot. Versions, formats, URLs, guidance and the law change. Re-check anything time-sensitive against its source before building on it, and record what changed in the pull request (PHASE-3.md 2.7). This is not legal advice: the legal and data protection sections are analysis for the data steward and the project lead to decide on.
