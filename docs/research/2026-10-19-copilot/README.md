These four notes are the evidence behind `docs/build/PHASE-4.md` and its code book. Research agents wrote them on 19 October 2026 by checking primary sources (the FastAPI, Starlette, Neo4j, APOC, driver and Ollama sources at fixed tags and commits, PyPI and Docker Hub, the Neo4j manuals, the AI Act and UK legislation, regulators' and standard setters' guidance, and the papers on natural-language interfaces to databases) and, where they could, by running code. ## Where the build spec decided differently

The spec wins where it differs from a note; the notes keep what was found on the day.

1. **Who routes a question.** `copilot-nl-to-graph.md` 8.1 proposes a model-first pipeline: a deterministic shortlist of templates, then a small model choosing one and a second call filling its slots. The spec routes with deterministic patterns alone (7.2.4) and makes the model optional and off by default (7.8): it is asked only about questions no pattern matched, in one call for the template and the slots, and the copilot needs no model to answer the benchmark and every committed set. A reading the model proposes is never answered at once: the copilot shows it, and the person confirms it before any query runs. The reasons are the note's own findings on determinism and abstention (`local-llm-runtime.md` 2).
2. **Grounding across scripts.** The note recommends matching names across scripts with name symbols (as Phase 2's `keys` package and OpenSanctions do) and fuzzy matching with calibrated thresholds. The spec grounds by an exact name key over every name the records give an entity, in its own script, and offers close names only as suggestions (7.2.3, 7.2.5): a name in another script matches when a record gives that name, as B4 shows. The key keeps accents and other marks, because removing them makes different names equal in many scripts (Devanagari and Thai vowel signs, for example), so a name typed without its accents is offered as a close name and never taken. Cross-script and fuzzy matching belong to entity resolution (Phase 2), whose results the copilot reads; a near match inside the copilot would answer silently about someone else.
3. **The benchmark questions.** The note's B4 asks which records were merged into a person, and its B6 explains an alert by its id. The spec's B4 asks for the directorships of a person named in Cyrillic, because the in-memory oracle does not merge records and the resolution explanation is the entity page's (C3 1.1.0); its B6 names the company ("Why was Calvane Holdings Ltd flagged?"), and the alert-id form is among the rewordings. There is no `merged_records` template in Phase 4.
4. **Exposure and cycles.** The note's T07 covers PEP and RCA exposure as well as sanctions, and its T11 searches for payment cycles of length 2 to 6. The spec's `sanctions_proximity` covers listed sanctions only (a person's own PEP flag is answered by `list_status`), and `circular_payments` reports the circular-flow alerts of the latest detection run instead of searching cycles itself, so that the copilot and the detector never disagree about what a cycle is.
5. **Template fields.** The note's catalogue has fields for status, owner, Cypher variants, result contracts and tests per template. The spec's templates name an operation instead (7.2.1): the query files belong to the port, their tests to the port and the sets, and their owners to CODEOWNERS.
6. **Refusals.** `copilot-legal-security.md` 7.2 proposes refusals as templates of the catalog. The spec refuses with two ordered screens and fixed texts (7.4.1), before and after routing, so that a refusal never depends on a template matching; only questions about the copilot itself ("are you an AI?", "is my question kept?") have a template (`about`).
7. **The held-out set.** The note proposes H1 (100 paraphrases from at least three writers per question), N1 (40 negative questions), a fresh H2 of 50, three runs per item, and reports with coverage, false refusals, RS(0) and RS(10). The spec sizes the set by Assignment 5 (three questions per card and three negative questions per writer, at least three writers per card), runs it once (the pattern router is deterministic; a second run only in model mode), writes a fresh batch only when a set changes, and reports items, cards, answered precision and the counts per family and card (7.7.4).
8. **The offline run.** The note runs the benchmark with network access disabled for the API, Neo4j and Ollama containers, and `local-llm-runtime.md` 8.4 adds a capture of outbound connections. The spec runs the three sets on a fresh Neo4j with the laptop's network switched off, checked by `scripts/network_off.py` before anything runs (7.7.5), which also fails when a proxy still answers or when the Neo4j plugins are missing from their folder; it involves no model, and the model's own offline check belongs to its measurement (7.8.5).
9. **Recorded model replies.** `local-llm-runtime.md` 8.3 proposes recorded responses of a real model, refreshed by a human, and a fake Ollama server in a Compose test profile. The spec tests the router against canned replies in `httpx.MockTransport` only (7.8.3), because a recorded reply would freeze one machine's output and nothing in CI may depend on a model.
10. **The audit log's fields.** `copilot-legal-security.md` 6.3 lists candidate counts, R-REAL withheld counts, the profile and a data snapshot id, and two latencies. The spec's allowlist (7.6.3) counts choices instead of candidates, in coarse buckets (0, 1, 2 to 9, 10 to 99, 100 or more), has no withheld count (the copilot refuses with a code rather than withholding), no profile or snapshot id (the API does not know them), and one latency. The note describes an audit log without personal data; the spec treats the log as personal data all the same, because its counts and its day can narrow down what was asked and, on a machine one person uses, it records that person's use: it is kept for 1 to 90 days (30 by default), read by the data steward only, and written under the real profile's folder when the API serves real data. The note's view, export and delete functions for users are not built: the log is a folder of daily files, deleted by retention.
11. **The consultation log.** The note proposes an opt-in consultation-log mode for law-enforcement deployers. The spec describes it for deployers and does not build it (7.6.4): it would hold personal data, so it belongs to the deployer's systems.
12. **Other languages.** The legal note's tests ask for refusals in English and at least one other language, on both parser paths. Phase 4 takes English questions only (0.5 decision 12): the refusal set is English, the model path is tested with a fake.
13. **The driver.** `api-readonly-cypher.md` 3 recommends the async driver in the lifespan, `telemetry_disabled=True` and a short retry window. The spec keeps Phase 1's sync driver (0.5 decision 11) and its settings, reads through explicit transactions (which the driver does not retry), and bounds concurrency with two slots instead of an `asyncio.Semaphore`.
14. **Outbound reads from the server.** The note describes `internal.dbms.cypher_ip_blocklist` (internal and undocumented) and `dbms.security.allow_csv_import_from_file_urls`. The spec sets neither: with no free Cypher, every query a committed file planned in CI (7.5.2), and the procedure allowlist, it does not depend on an undocumented setting.
15. **Pagination.** The note proposes keyset cursors. `GET /runs` returns the 50 newest runs, and the copilot's lists stop at fixed limits that the answers state; no cursor is needed in Phase 4.

## Facts added after the notes

These were checked against primary sources on 19 October 2026, while the spec was written and reviewed, and the spec relies on them.

1. **Neo4j's query log** is an Enterprise feature, which logs parameters by default (`db.logs.query.enabled`, "This feature is available in the Neo4j Enterprise Edition", and `db.logs.query.parameter_logging_enabled`, default true; Operations Manual 5, docs-operations commit 9fe3944 of 9 October 2026). Community Edition keeps no query log; a deployer on Enterprise must switch parameter logging off (7.6.5).
2. **The full-text analyzer.** A full-text index "analyzes both the indexed values and the query string" (Cypher Manual 5, `indexes/search-indexes/full-text-indexes.adoc`), and the default analyzer is `standard-no-stop-words` (`db.index.fulltext.default_analyzer`, Operations Manual 5, configuration settings): Lucene's standard tokenizer, which follows the Unicode word-break rules (an apostrophe or a full stop between letters does not end a word), with lower-casing per character and no stop words. So the copilot builds its full-text query from the words as they were written, not from its own name key, and the in-memory oracle splits names as the index does (7.2, 7.3).
3. **Notifications of an empty test graph.** Neo4j reports a label, relationship type or property key that the database does not hold as notifications 01N50, 01N51 and 01N52 (Cypher Manual 5, `planning-and-tuning/query-tuning.adoc`, "01N50: Label does not exist"). Phase 3's EXPLAIN test allows exactly these three; the copilot's EXPLAIN test does the same and fails on every other warning (M4.4).
4. **Plugins at container start.** "The Neo4j Docker image includes a startup script that can automatically download and configure certain Neo4j plugins at runtime" (Operations Manual 5, `docker/plugins.adoc`): the 5.x entrypoint installs a plugin named in `NEO4J_PLUGINS` from the image when its jar is there and otherwise downloads it (docker-neo4j, `docker-image-src/5/coredb/docker-entrypoint.sh` and `neo4j-plugins.json`). Whether the Community image holds the Graph Data Science jar was not confirmed (UNVERIFIED). So both Compose projects mount a plugins folder filled once while online, `scripts/network_off.py --plugins` checks it before the offline run, and the operator rehearses the offline start once (7.7.5, M4.6).
5. **What the driver logs.** The Python driver 6.4.1 logs each query it sends, with its parameters, at DEBUG (`neo4j/_sync/io/_bolt/_bolt5.py`), so a debug setting would write names from questions to a log; the API and the CLI hold the `neo4j`, `httpx` and `httpcore` loggers at WARNING whatever the root level (7.6.5).
6. **Errors the API must map.** The driver 6.4.1 classifies the memory-limit errors (`Neo.TransientError.General.TransactionMemoryLimit`, `Neo.TransientError.General.MemoryPoolOutOfMemoryError`) as `TransientError`, not `ClientError`, and Starlette 1.8 answers an exception that no handler takes with a plain-text 500. The API maps every database error to a problem response and contains any other exception in a fixed one (7.5).
